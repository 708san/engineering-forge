# 開発体制設計
入力: 人間の構想・原文参照、既存資産、許可済み制約、現在の能力。製品カテゴリは必須でない。
1. `../../../architect-v0.5.md` と `../../../requirements.md` の不変条件を読む。既存の正本、保護条件、変更範囲を確認する。
2. 実際に起きる現象、状態、利用者、境界、失敗、未知の要素を先に分析する。`discover-intent` を必要時利用。初期30領域はこの後で見落とし点検に使い、固有領域を追加する。
3. 成果を定義し、必要な専門知識を `research-knowledge` で補い、`design-method` で開発方法を構成する。小規模なら一つの作業で処理する。
4. `design-organization` と `design-operations` により、責任、協調、技術・データ・GitHub・環境・配布・保守の方針を設計する。成果・リスクから品質条件を導く。
5. 既存の正本と区別した候補を生成し、`review-blueprint` の観点で自己レビューまたは独立評価を依頼する。重大な不足は限定保留とし、独立作業を継続する。
6. `../../../schemas/blueprint.schema.json` に従う候補と、必要に応じた独自成果物、根拠、代替案、未決定事項、次の作業を提出する。正式採用は別の変更統制。形式適合は内容の妥当性を保証しない。
停止: 設計目的を達成、予算到達、必要権限なし、または安全に進められる作業なし。未達を明記する。
