# 開発インフラと運用設計
要求・成果・リスク・既存設定・利用環境を確認し、各事項を必要な粒度で定義する。未登録の環境や運用も考案する。
- 技術・アーキテクチャ・インターフェース・データ・実行環境の選択理由、代替案、制約、失敗条件を明記。実現性が不明なら技術試行を設計する。
- GitHub: リポジトリ境界・公開範囲、ブランチ、コミット、Push、PR（変更統合申請）、マージ、Issue、並行作業、保護、検査、復旧。許可のない外部変更は行わない。GitHubの機能・契約・権限は環境別に確認する。
- データ: 正本、機密性、利用許諾、保存・削除・移行。信頼境界と最小権限を定義。秘密を試験データに使わない。
- 品質: 成果に対応する検証・妥当性確認、条件、証跡、独立性、未実施時の扱い。実配布物・実運用への適用条件も考える。
- 配布・保守: 版、依存、公開条件、復旧、障害対応、互換性、廃止。不要なものは理由を記録し省略する。
- 設定は候補生成→差分→許可→適用→動作検証の順。宣言・生成・読込・強制を区別。実行権限がない場合も設計候補は出せる。
出力: 技術・環境・GitHub・品質・運用方針、正本、適用状態、holds。実際の操作は別の権限に従う。
