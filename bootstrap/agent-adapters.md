# 実行環境に対応したエージェント候補（v0.11-dev）
役割設計（誰が何を担当し、何を根拠に判断するか）と実行環境への設定生成を分離する。AIはプロダクト固有の役割を自由に考案する。単一の担当で十分な場合は追加エージェントを作らない。サブエージェントの数や名前に基づく製品分類はない。
## 生成契約
まず blueprint.schema.json に従う開発体制候補を作る。ネイティブエージェントが必要で、利用環境に対応した機能がある場合のみ、別途次の形式で agent-spec.json を作る。
```json
{
  "project_id": "PROJECT-EXAMPLE",
  "agents": [
    {"role_id": "ROLE-DESIGN", "name": "forge-material-trace",
     "description": "素材応答の分析が必要な場合に使用",
     "instructions": "対象の正式仕様と試験条件を確認し、観測と仮説を分離して評価結果を返す。"}
  ]
}
```
これは形式例のみで、特定の役割を採用する指示ではない。role_id は候補内で存在する役割を指す。name は既存の組込みエージェントを誤上書きしないよう forge- で始める。名前・説明・担当手順はAIが案件ごとに記述する。空配列も可能。
    python3 -B forge.py agents BLUEPRINT.json AGENT-SPEC.json
出力はJSONで、codex_files は相対パスとTOML本文、portable_roles は役割・目的・責任・知識・担当手順の対応。対象に書き込まず、起動しない。生成候補を別ディレクトリに保存し、preview・integrate と正式なレビューに従って必要なものだけ適用する。
## Codex
公式サブエージェント設定の必須3項目（name / description / developer_instructions）を .codex/agents/ の候補に変換する。TOMLの構文と内容の往復を検査する。モデル、sandbox、MCP、ネットワーク等の上書きはこのアダプターで生成しない。追加設定が必要な場合は別途公式仕様と権限を確認する。
出力から実際のネイティブ読込、起動、権限制御、独立性は判断できない。導入後は正しいエージェントが利用でき、対象の指示と役割を読んで許可範囲内で実行したことを確認する。
公式資料: https://learn.chatgpt.com/docs/agent-configuration/subagents （2026-11-28確認）
## ChatGPT
portable_roles を役割別作業契約として、利用可能な別セッションや作業機能へ渡せる。同一セッションで役割を切り替えた場合は自己レビューであり、独立したサブエージェントが起動したとは報告しない。通常のChatGPTにCodex用TOMLの実行機能があるとは仮定しない。
## 制約
構造変換のみ。担当指示の意味・正当性・安全性・権限・正式要求との一致は別のレビューが必要。生成設定は信頼境界ではない。実際の作業契約には対象版、許可、入力、成果、検証、停止条件を個別に指定する。固定ファイル名はアダプターの出力形式だけで、プロジェクトの開発方法は制約しない。
