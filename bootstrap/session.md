# 正本からの作業契約と再開（v0.14-dev）
共通レコードを採用しているプロジェクトでは、別の進捗表や作業契約に同じ情報を二重転記せず、既存のTask・Role・AcceptanceCriterion・Test・Evidence・Baselineから作業候補を導出できる。小規模案件や既存の管理方式が適切な案件では使わなくてよい。
    python3 -B forge.py session PROJECT_ROOT RELATIVE_MANIFEST.json
    python3 -B forge.py session PROJECT_ROOT RELATIVE_MANIFEST.json --observe-git
後者はクリーンなGit作業領域のHEADを取得する。記録保存先と検証するコードが異なる場合は --target CODE_WORKTREE を使う。Gitを観測する場合、基準のsource_commitが未確認または取得HEADと異なると再確認対象。Gitを観測しない場合は版を実測したとは報告しない。記録の保存コミットをその記録自身に埋め込む必要はない。確認のために人間の未コミット変更を勝手に退避・破棄しない。
## 契約と候補
- Taskの目的・対象・対象外・基準版・完了条件・予算・停止条件、Roleの責任・判断範囲・入出力・検証・エスカレーション、関連レコードの参照を抽出する。
- 操作名の文字列一致でTaskとRoleの宣言の積集合を示す。不一致は要レビュー。操作名の意味、実際の権限、委任の真正性は認証しない。生成された契約を実行許可とみなさない。
- activeなTaskの明示されたdepends_onを辿る。他種別・過去版への依存は意味レビューが必要。親子だけでは実行依存としない。blocked/paused/cancelledは自動再開しない。未完了前提がある場合は依存範囲を保留し、無関係な候補を別に示す。
- 完了記録は、同じ基準のactiveなTestとEvidence、全受入条件、環境、有効性、結果・ハッシュの記載を照合する。関連する複数の試験に未実施や失敗があれば都合のよいpassだけを選ばない。構造的なreported_pass / recorded_doneは実測の認証ではない。
- 未登録拡張は参照した作業を要レビューとし、無関係な候補を残す。別途依存関係の意味を確認する。
終了0は報告成功、2は基準・証跡・未登録拡張・契約等の要確認、1は検査不能。next_candidatesは許可済み実行キューではない。契約の内容・作業対象版・利用環境・保護条件・実際の権限をAIと責任主体が確認する。
## 通常の開発サイクル
1. 対象の入口、最新の正本と作業状態を読む。利用環境の実能力を確認する。
2. sessionや既存の課題管理から候補を選び、作業契約を具体化する（対象パス・入力・成果・並行作業の排他・実行権限を補う）。判断待ちは依存範囲だけに限定する。
3. AIが許可された範囲で実装・検証する。必要なら専門役割を考案し、既存の作業体制を再設計する。別エージェントが使えない場合は自己レビューと明記する。
4. 実行した検証と実際の成果物版を保存し、変更影響を調べ、必要なら独立レビューを行う。保護条件の変更は別管理基準とのguard比較を行う。
5. 許可範囲で統合・記録を更新し、次の作業を選ぶ。完了、予算、重要判断待ち、実行可能な独立作業がない場合に停止する。候補リストから自動実行はしない。
本機能は読み取り専用の補助であり、自律AIランタイムやスケジューラーではない。ファイル・基準・証跡の真正性、作業範囲の強制、全依存の完全性、正式な採用は別工程。AIが利用できない場合も記録は人間が読める。基盤の再参照を通常の開発に必須としない。

## 固定レコードの内容指紋
`python3 -B forge.py baseline PROJECT_ROOT RELATIVE_MANIFEST.json` はBaseline.compositionの版付き参照が指すレコードをID・版でソートし、UTF-8のキー順固定・空白なしJSON（encoding=forge-record-composition-v1）としてSHA-256を計算する。空、重複、自己参照、欠落は拒否。既存のsnapshot_sha256に対し内容一致を表示する。未一致は終了2、構造エラーは1。旧fixtureの0埋めは意図的な未検証例であり合格としない。sessionも未一致を保留とする。正式な基準候補を作る際のみ計算値を保存し、既存基準を変更検出の回避目的で再ハッシュしない。独立した旧基準とのguard比較は引き続き必要。
指紋は列挙されたレコードのみを対象とし、全ツリー、推移的参照、外部実行環境、署名、承認を証明しない。Pythonの正規化方式であり他言語共通の標準正規化を保証しない。証跡の対象コード版と証跡の保存版は分ける。

作業の受入条件と直接紐付く規範的レコード（Intent/Goal/Principle/Requirement/Constraint/Policy）はactiveかつ現在のBaseline.compositionに固定されている必要がある。完了の記録判定には関連するactiveなTest・Environmentも基準に固定する。テスト手順だけを書き換えて以前の証跡を有効扱いしない。まだ試験がない提案タスクは受入条件が固定済みなら設計・実装候補になり得る。固定集合の網羅性や意味は別途レビューする。
