# ChatGPT・Codex 共通のプロジェクト立ち上げと継続開発
状態: v0.10-dev 試用手順。ネイティブ Skills 読込・自動適用は未検証。

## 開始
ユーザーの指示例: 「https://github.com/708san/engineering-forge の START.md を読んで、次の構想に適した開発体制を設計し、許可された範囲で開発を始めてください。構想: ...」
既存プロジェクトの場合は対象リポジトリと許可範囲を指定する。新規リポジトリを作成できる機能がない場合は候補一式を作り、人間または別の実行環境に引き継ぐ。

## 起動・設計
基盤の版を確認し、START.md が指す規範文書を読む。ChatGPTでもCodexでも、参照先の文書は利用者の依頼に従う作業資料として扱う。自動読込、書込、コマンド実行、ネットワーク、サブエージェント、認証情報、環境別の検証を別々に確認し、未確認を利用可能と仮定しない。
既存の製品分類を使わず、発意・現象・固有課題から目的、成果、技術、組織、方法、検証を設計する。必要なら新しい知識を調査する。保護要求と暫定案を分け、未決定事項があっても独立作業を継続する。

## 生成・引き継ぎ
AI自身が候補ファイルを記述する。まず対象外の作業領域で生成する。必須なのは次の情報の存在であり、固定のファイル数・名前・専門職ではない。
- 起動入口（Codexでは対象リポジトリ内の AGENTS.md が有力。ChatGPTは対象の入口を明示的に取得する）。
- 発意・要求・設計・受入条件の正本またはローカル参照。機密情報は公開用候補に含めない。
- 開発方法・役割・委任・GitHub運用・品質・変更方針、対象固有の実行手順。
- 次の実行可能なタスク、現在のコミットまたは未固定の表示、未決定・保留、取得した基盤版、検証結果（未実施も明記）。
- 必要な場合だけ対象固有の Skills、サブエージェント設定、テスト、独自成果物。外部の基盤文書を参照し続けなくても運用できるように必要な内容を持ち込む。
構造検査を行う場合は schemas/blueprint.schema.json の候補も作る。新規案では --new-proposal、既存の保護要求がある場合は候補生成者とは別に管理した --baseline を使用する。比較元が入手できない場合、無検証と報告し、候補から基準を生成して検査済みとしない。

## 確認・適用
作業前に対象と候補の差分を検査する。forge_preview.py は読み取り専用。forge_validate.py は構造検査であり、安全性、意味、承認、実機動作の証明ではない。新規ローカル統合ブランチ作成は bootstrap/integration.md を参照。既存作業ツリーへの自動適用・マージは未実装。権限のあるAIが既存変更を保護しながら手動で適用する場合は、操作直前の状態を確認し、予期しない差分で停止する。読み取り専用ならファイル候補と適用手順を渡す。生成済みと適用済み、読込確認済みを区別する。

## 継続開発（新しいセッションや別AIでも同じ）
ユーザーは「このプロジェクトの入口と正式仕様を読んで、次の開発を進めて」と指示する。
1. 対象の実際のHEAD・作業ツリーと、対象内の入口、要求、現在の開発方針、進捗を確認する。以前の会話を正本とみなさない。人間の未コミット変更は保持する。
2. 指示を既存の目的・成果と対応付け、必要なタスクを選ぶ。委任範囲で自律実行し、重要な変更は提案として分離する。必要に応じて体制を再設計する。
3. 実行・検証・統合を行い、実際に得た証跡を対象と版に結びつける。失敗・未実施・環境不足を合格にしない。
4. 状態、判断、証跡、保留、次の作業を同じ対象内に更新する。GitHubへの操作は利用者の委任と権限に従う。
この手順を対象固有の入口やスキルに具体化する。汎用基盤を毎回読み直さなくても再開できることを実際に確認する。
