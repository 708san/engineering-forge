# 初めて使う（v0.11-dev、試用版）
## ChatGPTでもCodexでも同じ
人間が入力するのは基本的に構想・希望・許可範囲だけ。例えば:
> https://github.com/708san/engineering-forge の START.md を読み、私と共同で以下のプロダクトの要件・開発体制を設計し、合意済みの範囲で開発を開始してください。構想: ...
試用版を使う場合は、URLに加えレビュー対象のコミットを指定する。main に試用版が統合されたと仮定しない。必要に応じて AI 自身が基盤の版を確認して取得する。参照できなければアクセスできるアーカイブやファイルを求める。
AIは製品固有の課題、技術、方法論、必要な役割と品質を考案する。既存テンプレートや必須エージェント数から始めない。構想段階では新規リポジトリの作成・実装を自動的に行わない。人間の重要判断と実際の操作許可を確認し、委任内の独立作業は続ける。
## ChatGPT
GitHub連携や取得機能で基盤・対象を読む。通常の読み取り専用環境では候補ファイルと差分・次の作業を渡す。書き込みや実行が使える環境では許可された操作を行う。GitHub URLを読むだけでSkillsの自動インストールが成立するわけではない。APIキーや追加契約は基盤の必須条件ではない。
## Codex
対象プロジェクトを作業領域に指定し、同じ指示を出す。基盤のリポジトリを対象と別の作業領域で取得するか利用可能な読み取り機能で必要なファイルを読む。ローカルの実行が可能なら構造検査・導入・引き継ぎ・影響検査を任意利用する。生成後に対象の AGENTS.md / 専用Skills が実際に読まれているか実機確認する。基盤の全Skillsや例を対象へ一律コピーしない。基盤そのものの書き換えを対象開発と混同しない。
## 生成から開発へ
1. 発意・必要成果・未決定事項を整理。開発方法・組織・技術・品質を設計する。
2. 対象固有の入口、正本、運用方針、次の作業を候補として生成する。必要な場合だけ専用Skillsやエージェント設定を作る。
3. 生成候補を評価し、既存資産を保持して導入する。Gitが使える場合は integration.md の統合候補ブランチを利用可能。権限確認、差分確認、実際の採用は別工程。
4. 対象のコード・テスト・仕様を開発する。結果、現在の版、残存課題を対象に保持する。
5. 次のセッションでは「このプロジェクトの入口・正式仕様・現状を確認して、開発を続けて」と指示。必要に応じて handoff.md / change-impact.md を利用する。通常の継続開発には基盤本体への接続は不要。
## AIが利用する任意ツール
利用者が毎回コマンドを入力する必要はない。実行環境と権限の範囲でAIが使う。構造・要求比較 forge_validate.py、差分 forge_preview.py、導入候補 forge_integrate.py、引き継ぎ forge_handoff.py、変更影響 forge_impact.py。生成・実機読み込み・テスト・正式採用・権限強制を混同しない。

共通コマンド `python3 forge.py doctor --target TARGET`（対象未作成時は --target なし）でローカルの存在確認を行える。`python3 forge.py --help` から preview / validate / handoff / integrate / impact を呼べる。各コマンドの引数は元のスクリプトと同じ。ネットワーク、GitHub書き込み、ネイティブSkills、操作承認は別途確認する。doctorの終了0は観測出力成功であり、開発準備完了ではない。

URLを毎回渡さずに済む任意のskill-onlyプラグイン候補も用意する。`bootstrap/distribution.md`。実機インストール・読込は未検証。
