# 初めて使う（v0.18.0-preview.5）
[4つの利用場面別の具体的な指示例](use-cases.md) を参照。
## ChatGPTでもCodexでも同じ
人間が入力するのは基本的に構想・希望・許可範囲だけ。例えば:
> https://github.com/708san/engineering-forge/tree/v0.18.0-preview.5 の START.md を読み、私と共同で以下のプロダクトの要件・開発体制を設計し、合意済みの範囲で開発を開始してください。構想: ...
リリースタグ v0.18.0-preview.5 または対応する固定コミットを指定する。main に試用版が統合されたと仮定しない。必要に応じて AI 自身が基盤の版を確認して取得する。参照できなければアクセスできるアーカイブやファイルを求める。
AIは製品固有の課題、技術、方法論、必要な役割と品質を考案する。既存テンプレートや必須エージェント数から始めない。構想段階では新規リポジトリの作成・実装を自動的に行わない。人間の重要判断と実際の操作許可を確認し、委任内の独立作業は続ける。
## ChatGPT
GitHub連携や取得機能で基盤・対象を読む。通常の読み取り専用環境では候補ファイルと差分・次の作業を渡す。書き込みや実行が使える環境では許可された操作を行う。GitHub URLを読むだけでSkillsの自動インストールが成立するわけではない。APIキーや追加契約は基盤の必須条件ではない。
## Codex
対象プロジェクトを作業領域に指定し、同じ指示を出す。基盤のリポジトリを対象と別の作業領域で取得するか利用可能な読み取り機能で必要なファイルを読む。ローカルの実行が可能なら構造検査・導入・引き継ぎ・影響検査を任意利用する。生成後に対象の AGENTS.md / 専用Skills が実際に読まれているか実機確認する。基盤の全Skillsや例を対象へ一律コピーしない。基盤そのものの書き換えを対象開発と混同しない。
## 生成から開発へ
1. 発意・必要成果・未決定事項を整理。開発方法・組織・技術・品質を設計する。
2. 対象固有の入口、正本、運用方針、次の作業を候補として生成する。必要な場合だけ専用Skillsやエージェント設定を作る。
3. 生成候補を評価し、既存資産を保持して導入する。Gitが使える場合は integration.md の統合候補ブランチを利用可能。権限確認、差分確認、実際の採用は別工程。
4. 対象のコード・テスト・仕様を開発する。結果、現在の版、残存課題を対象に保持する。
5. 次のセッションでは「このプロジェクトの入口・正式仕様・現状を確認して、開発を続けて」と指示。必要に応じて handoff.md / change-impact.md を利用する。通常の継続開発には基盤本体への接続は不要。
## AIが利用する任意ツール
利用者が毎回コマンドを入力する必要はない。実行環境と権限の範囲でAIが使う。構造・要求比較 forge_validate.py、差分 forge_preview.py、導入候補 forge_integrate.py、引き継ぎ forge_handoff.py、変更影響 forge_impact.py。生成・実機読み込み・テスト・正式採用・権限強制を混同しない。

すべての補助機能は任意。AIが必要時だけ使う。共通コマンド `python3 forge.py doctor --target TARGET`（対象未作成時は --target なし）でローカルの存在確認を行える。`python3 forge.py --help` から preview / validate / handoff / integrate / impact を呼べる。各コマンドの引数は元のスクリプトと同じ。ネットワーク、GitHub書き込み、ネイティブSkills、操作承認は別途確認する。doctorの終了0は観測出力成功であり、開発準備完了ではない。

URLを毎回渡さずに済む任意のskill-onlyプラグイン候補も用意する。`bootstrap/distribution.md`。実機インストール・読込は未検証。

タスクの依存関係や証跡の状態が複雑な場合は任意の progress コマンドを利用できる。文書が増えること自体を目的にしない。

共通レコード採用時は任意の session コマンドが次の作業候補と契約を示す。通常の依頼は従来どおり自然言語でよい。

開発方法に問題がある場合は `adaptation.md` に沿って必要な範囲だけ比較試行する。実装済みの補助ツールを全て使用する必要はない。

対応対象はChatGPTとCodexのみ。URL参照を標準とし、ネイティブプラグイン候補は実機で対応を確認できた場合だけ使用する。新規セッションで基盤を読み、生成後は対象プロジェクトのAGENTS.mdなどの入口を使う。

## 運用開始時の最小確認
新規: 「この構想をForgeで共同設計し、合意した範囲で実装してください」。既存: 「対象リポジトリの現在のHEAD・未コミット編集・既存AGENTS.md・テストを先に確認し、維持すべき資産と導入差分を示してください」。再開: 「前回の正式仕様、実装版、残タスク、実際の検証結果を読み、独立して進められる作業を続けてください」。最初の応答には取得したForge版、対象版（または未作成）、実際に使える読取/書込/実行能力、未決定の重要判断、次の作業を簡潔に含める。環境が読み取り専用なら候補と差分を渡す。AIに秘密鍵やアクセストークンを会話に貼り付けない。既存のAGENTS.mdを一律上書きせず、階層ごとの指示を読む。実機で読み込みを確認できない場合は明示して通常の参照方式を使う。

日常運用とフィードバックは `../OPERATE.md`。個人実運用評価版は利用者が通常の自然言語で改善点を伝えられる。公開Issueは任意で機密情報を含めない。
